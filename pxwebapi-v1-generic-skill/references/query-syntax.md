# The v1 query body and filter syntax

Everything about the JSON you POST to a table URL. All examples verified live on 2026-08-28 against
`https://data.ssb.no/api/v0/no/table/07459` (SSB),
`https://api.scb.se/OV0104/v1/doris/sv/ssd/BE/BE0101/BE0101A/BefolkManadCKM` (SCB) and
`https://bank.stat.gl/api/v1/en/Greenland/BE/BE01/BE0125/BEXST8.px` (Statistics Greenland).

---

## The envelope

```json
{
  "query": [ /* zero or more selection objects */ ],
  "response": { "format": "json-stat2" }
}
```

- `query` — required, may be empty (`[]`).
- `response` — optional, but **always set it**: the format you get when you omit it is installation-specific, and there are three answers, not two. Measured across all seven verified installations on 2026-09-04 — `json-stat2` at SSB, Finland and Estonia; PX at SCB and Greenland; PX-JSON (`{"columns": …, "data": …}`) at the Faroe Islands and Iceland. The PxWeb 1.0 spec prescribes PX, which two of the seven do.

A selection object is:

```json
{ "code": "<variable code from metadata>",
  "selection": { "filter": "<filter>", "values": ["<…>"] } }
```

`code` must match `variables[].code` from the table's metadata exactly, including case.
`values` is always an array of **strings** — quote numeric codes and the `top` count alike.

Variables you do not mention are handled by the elimination rules (below).

## Filters

### `item` — explicit codes

The default and the most common. Lists exact value codes.

```json
{ "code": "Region", "selection": { "filter": "item", "values": ["0301", "1103"] } }
```

Codes must exist in `values` for that variable. A code that does not returns
`400 {"error":"The request for variable 'Region' has an error. Please check your query."}`.

### `all` — wildcards

`*` matches zero or more characters.

```json
{ "code": "Tid", "selection": { "filter": "all", "values": ["*"] } }      // every period
{ "code": "Tid", "selection": { "filter": "all", "values": ["202*"] } }   // 2020, 2021, … 2026
{ "code": "Tid", "selection": { "filter": "all", "values": ["*M12"] } }   // every December in a monthly table
```

**Multiple wildcards in one list work.** Verified on both SSB and SCB:

```json
{ "code": "Tid", "selection": { "filter": "all", "values": ["199*", "202*"] } }
// → 1990…1999 and 2020…2026
```

The published PxWeb 1.0 specification says only one wildcard is allowed. That is outdated for
current builds, but may still hold on old installations — if a multi-wildcard `all` returns 400,
split it into several requests or switch to `item`.

**`?` single-character masking is not supported.** This is a known gap in v1, not a syntax error
on your part.

### `top` — the N newest or first values

```json
{ "code": "Tid", "selection": { "filter": "top", "values": ["5"] } }
```

`values` must hold exactly one positive integer, **as a string**. For a variable with
`time: true` this returns the N *latest* periods; for any other variable, the first N values
in metadata order.

`top` is what makes a query **rolling**: save it once and it keeps returning current data as
new periods are published. An `item` list naming a future period fails instead.

### `agg:{name}` — aggregations and groupings

Selects from a predefined grouping — five-year age bands, merged-municipality time series,
regional roll-ups:

```json
{ "code": "Region",
  "selection": { "filter": "agg:KommFylker", "values": ["F-03", "F-11"] } }
```

Two hard constraints:

- **Only explicit codes.** `"values": ["*"]` returns 400. Enumerate the members you want.
- **The aggregation is invisible in v1 metadata.** Neither its name nor its member codes appear
  in the `GET` response. See "Discovering aggregations" below.

The name after `agg:` is the `.agg` **filename without its extension**, so it can contain spaces
and punctuation — `agg:25-years classes` is a legitimate filter. An aggregation belongs to exactly
one valueset, which is why a name that works on one table often returns 400 on another. See
`px-files-and-classifications.md`.

Aggregation member codes are usually prefixed. At SSB, merged-municipality series use `K-` plus
the municipality number (`K-0301`) and county roll-ups use `F-` plus the county number (`F-03`).
A few tables replace the hyphen with `_` or `.` because the code points at a different code list
(e.g. `K_` in SSB table 06913). Prefixes are agency- and table-specific — always confirm against a
real code list rather than guessing.

Why it matters: after a municipality reform, `item` codes give you the *old* boundaries with
broken time series. `agg:` gives a consistent series where the new municipality's history is the
sum of its predecessors.

### `vs:{name}` — alternative value set

Selects from a different set of values for the same variable:

```json
{ "code": "Region", "selection": { "filter": "vs:NUTS", "values": ["01", "02"] } }
```

Like `agg:`, invisible in metadata. If a query generated by an agency web front end contains a
`vs:` filter over what are simply the table's ordinary codes, you can usually replace the whole
filter with `"item"` and keep the same `values`.

## Time periods, and the TLIST that never arrives

**The PX format declares its time scale; json-stat does not, and v1 does not pass it on.** In the
PX file the time variable is written with `TIMEVAL(...)=TLIST(<scale>)`, where the scale is one of:

| TLIST | Frequency | PX-internal period format |
|---|---|---|
| `A1` | Annual | `CCYY` |
| `H1` | Half-year | `CCYYH`, H = 1–2 |
| `Q1` | Quarterly | `CCYYQ`, Q = 1–4 |
| `M1` | Monthly | `CCYYMM` |
| `W1` | Weekly | `CCYYWW` |

TLIST also guarantees the periods are consecutive. **None of this survives into the API.** In v1
the time variable carries only `"time": true` — no frequency, no first/last period — and the
json-stat2 data response adds only `role.time` naming the dimension. json-stat2 has no field for
periodicity at all, so even a perfect serializer could not carry it. PxWebApi **v2** restores the
information as `timeUnit` (`"Annual"`, `"Monthly"`, …) on the *table* resource — but still not
inside the json-stat2 document.

So on v1 you must infer the frequency from the value codes. Observed at SSB:

| Frequency | Actual API value codes |
|---|---|
| Annual | `2026` |
| Monthly | `2025M12` — note the `M`, unlike TLIST's bare `CCYYMM` |
| Quarterly | `2020K3` at SSB and SCB (`K` for *kvartal*); other installations use `Q` |

The `M`/`K`/`Q` letter is a PxWeb presentation convention, not the TLIST format — do not construct
codes from the PX specification. **Read the actual `values` array and copy its shape.**

### Time codes are not required to be dates

The strongest reason not to parse time codes: they need not encode a period at all. Statistics
Greenland's `AL/AL10/ALXALK4.px` has a variable literally named `time` with `"time": true`, whose
codes are `0`–`50` while its **labels** are the years. `top(3)` returns:

```json
"time": { "category": { "index": { "48": 0, "49": 1, "50": 2 },
                        "label": { "48": "2023", "49": "2024", "50": "2025" } } }
```

The year exists only in `label`; the code is a sequence number. Consequences:

- **`item` filters take the code, not the label** — ask for `"50"`, never `"2025"`.
- Any client that regexes `\d{4}(M\d\d)?` against time codes breaks on this table.
- `top(N)` still works correctly, because it operates on position rather than on parsed dates.
  This is a good reason to prefer `top` over an `item` list whenever "the most recent N periods"
  is what you actually mean.

Practical rule: **use `top` for recency, `all` with a wildcard for a span, and reach for explicit
`item` codes only after reading `values` and `valueTexts` together.**

## Discovering aggregations

v1 gives you no way to list them. In rough order of reliability:

**1. Ask the installation's v2 API, if it has one.** v2 lists every code list in metadata, and the
ids map onto v1 filters by swapping the underscore for a colon — v2 `agg_KommFylker` is v1
`agg:KommFylker`. The three-step worked example is in `v1-vs-v2.md` under "Using v2 to fill v1's
gaps". Note the irony before reaching for it: the installations that run v2 are the ones that
needed this least, so on most v1-only installations you fall back to methods 2 and 3.

**2. Build the selection in the agency's web front end and export the query.** Most PxWeb UIs
have an "API query for this table" button on the results view that emits a complete v1 body,
aggregation names and member codes included. Copy it verbatim, then edit.

**3. Ask the agency's classification service.** SSB's Klass API
(`https://data.ssb.no/api/klass/v1/`) publishes the underlying classifications and their
correspondences, which is where most `agg:` groupings come from.

## Elimination — what happens when you omit a variable

The rules, from the PxWeb 1.0 specification and confirmed live:

| `elimination` | Elimination value exists? | Result of omitting the variable |
|---|---|---|
| `true` | yes | Only the total is returned |
| `true` | no | All values are aggregated into one |
| `false` *or absent* | — | **All** values of the variable are returned |

`elimination` and `time` both default to `false` when absent from metadata.

**The two routes to a total can coexist, and metadata will not tell you which you have.** In
Greenland's `BEXST8.px` the `age` variable carries both an explicit `-1` = "Total" among its
`values` *and* `elimination: true`; selecting `-1` and omitting the variable return the same
figure (verified). At the other extreme, SSB's `Kjonn` in 07459 has no total in `values` and no
way to obtain one except omission, while SCB lists an explicit `TotSA`/`TotSa` code. Scan
`valueTexts` for a "Total" / "I alt" / "Hele landet" entry before deciding which route a table
needs — rule 1 above fires only when such a value exists.

Two verified illustrations:

```
POST .../ssd/BE/BE0101/BE0101A/BefolkManadCKM   {"query": [{"code": "Tid", …top 1}], …}
  Region (elimination: true) → gone from the response
  Kon    (elimination: true) → gone from the response
  Alder  (elimination absent → false) → all 134 age values returned
  → id: ["Alder", "ContentsCode", "Tid"], size: [134, 1, 1]
```

```
POST https://data.ssb.no/api/v0/no/table/07459   {"query": [], …}
  Region, Kjonn, Alder (all elimination: true) → gone
  Tid (time: true, elimination absent) → all 41 years returned
  → id: ["ContentsCode", "Tid"], size: [1, 41]
```

Consequences worth planning around:

- **Eliminated variables vanish from the response.** They are absent from `id` and `dimension`
  rather than appearing with size 1, so the payload carries no record of what was collapsed.
  Say so yourself when presenting the numbers.
- **Omitting the time variable is a feature.** It returns the full series including periods that
  do not exist yet, which is how "whole time series" queries survive new publications.
- **Omitting a non-eliminable breakdown is a trap.** It silently multiplies your cell count by
  that variable's size and can push you over the limit.
- **The total is often not a selectable code.** Where `elimination: true`, omission is usually the
  only way to get the total. Some installations do publish an explicit total code (SCB uses
  `TotSA` on `Alder`, `TotSa` on `Kon`; SSB's `Kjonn` uses `0` in some tables and has no total in
  others) — check `valueTexts` before assuming either way.

## Worked examples

**Single region, latest three years, eliminating sex and age** (SSB 07459):

```json
{ "query": [
    { "code": "Region",       "selection": { "filter": "item", "values": ["0301"] } },
    { "code": "ContentsCode", "selection": { "filter": "item", "values": ["Personer1"] } },
    { "code": "Tid",          "selection": { "filter": "top",  "values": ["3"] } } ],
  "response": { "format": "json-stat2" } }
```

**County-level series that survives municipality mergers** (SSB 07459, aggregation):

```json
{ "query": [
    { "code": "Region",       "selection": { "filter": "agg:KommFylker", "values": ["F-03", "F-11"] } },
    { "code": "ContentsCode", "selection": { "filter": "item", "values": ["Personer1"] } },
    { "code": "Tid",          "selection": { "filter": "all",  "values": ["*"] } } ],
  "response": { "format": "json-stat2" } }
```

**A variable code containing spaces, and no metric variable at all** (Statistics Greenland
`BEXST8.px`). `age` and `gender` are eliminated by omission; the response comes back with
`role: {"time": ["time"]}` — no `metric`, no `geo` — and no `unit` on any dimension, so the
measure ("persons") has to be read off the table title:

```json
{ "query": [
    { "code": "place of birth", "selection": { "filter": "item", "values": ["00", "03"] } },
    { "code": "time",           "selection": { "filter": "all",  "values": ["*"] } } ],
  "response": { "format": "json-stat2" } }
```

**Non-Nordic variable codes** (Statistics Finland `11ra.px` — note nothing is named
`Region`/`ContentsCode`/`Tid`, and the geography code embeds a classification date):

```json
{ "query": [
    { "code": "alue_23_20260101", "selection": { "filter": "item", "values": ["SSS"] } },
    { "code": "contentscode",     "selection": { "filter": "item", "values": ["vaerak-vaesto"] } },
    { "code": "timeperiod_y",     "selection": { "filter": "top",  "values": ["3"] } } ],
  "response": { "format": "json-stat2" } }
```

## cURL

The whole API is one POST, so cURL is enough for production use:

```bash
curl -d @query.json -X POST \
     -H "Content-Type: application/json" \
     https://data.ssb.no/api/v0/no/table/07459 \
     -o result.json
```

`-d @file` reads the body from a file, `-o` writes the response. On Windows shells, single quotes
in an inline body must be doubles — keeping the query in a file avoids the problem entirely.
