# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is **not** an application codebase. It is a Claude Code **Skill** package that teaches Claude how to query Statistics Norway (SSB) via the public PxWebApi v2 at `https://data.ssb.no/api/pxwebapi/v2`. There is no application runtime — changes here are documentation/prompt edits that get loaded when the `ssb-pxwebapi-v2` skill triggers.

There *is* a build step and a test suite, but they are unusual: `scripts/build_zip.sh` packages the distributable, and the Python checkers under `scripts/` treat every example URL, POST body and table ID written in the markdown as an assertion to verify against the **live** SSB API. Prose is the fixture set; drift upstream at SSB fails the build.

Upstream source of truth: https://github.com/janbrus/pxwebapi-skills/tree/main/ssb-pxwebapi-v2-skill (the repo was renamed from `ssb-api-v2-examples`; old URLs redirect)

## Commands

Requires Python 3.12+ (stdlib only — no dependencies) and `zip`/`unzip`.

```bash
# Verify every example URL, GET/POST query and table ID in SKILL.md + references/ + docs/
python3 scripts/check_examples.py            # add --quiet to hide OK lines
python3 scripts/check_examples.py --delay 1.0   # slower; use when rate-limited (429)

# Verify references/common-tables.md rows against /tables/{id}
python3 scripts/check_common_tables.py --quiet --delay 1.0
python3 scripts/check_common_tables.py --md references/common-tables.md   # check a single file
python3 scripts/check_common_tables.py --workers 4                        # parallel; ignores --delay

# Rebuild the distribution zip (required before committing content changes)
scripts/build_zip.sh                  # writes ./ssb-pxwebapi-v2-skill.zip
scripts/build_zip.sh /tmp/fresh.zip   # write elsewhere, e.g. to diff against the committed zip
```

There is no single-test flag; scope a run by pointing `check_common_tables.py --md` at one file, or by narrowing `--delay`/`--quiet` for a faster full pass. Both checkers exit non-zero on errors; `check_common_tables.py` warnings (title drift, stale `lastPeriod`) do **not** fail CI.

`.github/workflows/check-tables.yaml` runs two jobs — `check` (both Python scripts) and `zip-sync` (rebuilds the zip and `diff -r`s it against the committed one) — on push/PR touching `SKILL.md`, `README.md`, `CHANGELOG.md`, `references/**`, `docs/**`, `scripts/**` or the zip, and by hand via `workflow_dispatch` (Actions tab → *Run workflow*). There is **no scheduled run**: the Monday cron was removed on 2026-10-13 (maintainer's call), so SSB-side drift with no local change surfaces only on the next push or manual run. Run both checkers locally before a release.

### The `/savedqueries` safety rule

`check_examples.py` deliberately never issues `POST /savedqueries` — that would create persistent state on SSB's servers. Such examples are JSON-syntax-validated only. Keep this exemption if you extend the checker, and never "verify" a saved-query example by actually posting it. Since 1.6.2 the one `POST /savedqueries` example lives in `references/saved-queries.md`; the `GET /savedqueries/10119120` lines beside it are real GETs and are checked.

## Layout

- `SKILL.md` — the skill entrypoint. Frontmatter (`name`, `description`, `license`, `metadata.version`) controls when the skill auto-triggers; the body is the operational guide Claude follows. Keep triggers (Norwegian + English keywords for Norwegian official statistics) in the `description`. Structure: data-integrity rule → routing to sibling skills/tools → endpoint table → tool selection → language → 6-step workflow (Steg 1–6) → pitfalls → worked examples → fallback (which also carries the pointer to `troubleshooting.md`).

Since 1.5.0 the file is deliberately deduplicated: each rule has **one** primary occurrence in `SKILL.md` plus pointers, and detail lives in `references/`. Before adding a paragraph, grep for the term — if it already appears, extend the existing occurrence or the reference file instead of writing a second one. Terms worth grepping: `elimination`, `noteMandatory`, `top()`, `Lagre`, rate limit, `KOSTRA`, `KOK`. Since 1.6.5 the Dataintegritet bullets state the rule only. The detail behind them lives in `common-tables.md` (14746 alternatives, when not to use SSB's ready-made per-capita figures) and `troubleshooting.md` (discontinued and removed tables, successor via the table note or SSB's endringsside). That was the maintainer's call on 2026-10-23, so don't move it back.
- `references/` — deeper reference material loaded on demand:
  - `json-stat2.md` — table of contents, then «Slik leser du et uttrekk» (seven numbered rules, actions only, row-major indexing in rule 2), then the format: Dataset structure and indexing, a field table, `extension` at dimension and dataset level, `status`/`note`/`link`, what json-stat2 does not carry, tools. Since 1.6.2 rules come first and the format sections only describe; keep that split. Every field that comes from the PX file names its PX keyword in parentheses (`measuringType` ← `STOCKFA`, `noteMandatory` ← `NOTEX`, `status` ← `DATASYMBOL…`/`DATANOTECELL`; source: `PxTools/PCAxis.Serializers`, `JsonStat2Serializer.cs`), and the `extension.px` keys are PX keywords in lower case. SSB never sets `noteMandatory` or `categoryNoteMandatory` at dimension level (0 of 89, 2026-10-11) although the PxWebApi spec has them — notes per variable and per value are never mandatory at SSB, so don't reintroduce them as rules
  - `api-details.md` — SSB-specific operational info (publishing times, rate-limit headers, license)
  - `codelists-and-filters.md` — codelist/filter syntax: `codelist[Var]=agg_…`, `top(n)`/`from(x)`/`range(a,b)`, wildcards, plus the `outputValues[Var]` parameter and the finding that it is **not load-bearing** at SSB (identical data for `aggregated`, `single` and omitted; an invalid value returns HTTP 200 unvalidated — verified 2026-08-30). Don't reintroduce it as a requirement. Note prefixes: `agg_KommFylker` uses `F-`, `agg_KommSummer` uses `K-`, the age groups use `F00-04`; such codes give 400 without `codelist[Var]`, and `valueMap` (not the `agg_` prefix) tells whether a list sums. Includes KPI/COICOP groupings (`vs_CoiCop2018Kpi01`, `agg_CoiCop2018Kpi011`) — COICOP 2018 is UNSD's international classification, the codelists are SSB's own. Since 1.6.2 the order is: table of contents → general codelist rules → filter expressions (both within the first ~100 lines, because some agents only read the head of a file) → SSB-specific sections. Keep the headings «Regionale nivåer under kommune: bydel, delområde, grunnkrets» and «Næringskoder: SN2007 → SN2025» verbatim — `SKILL.md`, `troubleshooting.md` and `klass-vardok.md` point to them by name
  - `saved-queries.md` — saved queries: SSB's recommendation (a plain API URL with `top()`/`from()` for automation) first, then the `POST /savedqueries` body (`outputFormat` and `outputFormatParams` both mandatory), the GET endpoints, and old v1-era `ssb.no/statbank/sq/{id}` IDs still served via the API. Moved out of `SKILL.md` Steg 6 in 1.6.2 because saved queries are of marginal interest to users (maintainer's call, 2026-10-10); Steg 6 keeps the recommendation and a pointer. Don't move the detail back
  - `search-syntax.md` — pure Lucene query parser reference for `/tables?query=` (PxWebApi uses Lucene.Net under the hood). Non-Lucene search parameters (`pastDays`, `includeDiscontinued`) and Norwegian term choice belong in `SKILL.md` Steg 2, not here
  - `klass-vardok.md` — SSB's Klass (classifications) and VarDok (variable definitions) via URNs in `link.describedby` and ready-made `link.related` links, plus deriving the statistics shortname from `paths` before metadata is fetched. That derivation only holds when every path shares the third node; for the 504 cross-listed tables (KOSTRA plus e.g. 10484, 14662) `extension.metaid` is the answer and `paths[0]` is wrong for 76 of 450 active ones (sweep 2026-10-03). `subjectCode` narrows the candidates but leaves 178 of 504 ambiguous, and the `isPrimaerPlassering` flag from ssb.no's subject tree adds nothing on top (same 178), so don't build a heuristic on either. Since 1.6.5 it also has the date lookups `changes`, `codesAt` and `correspondsAt` (131 → 112 replaces knowing the yearly KOSTRA table ID). In `changes` the change date must fall strictly between `from` and `to` (`from` inclusive, `to` exclusive, and a change needs the day before in range too), or the answer is 0 rows with no error. Klass URLs carry no `.json` suffix — SSB deprecated it (API guide §1.7.1, 2026) — and Klass picks the format from `Accept` (`text/html` alone gives 500). `check_examples.py` GETs Klass URLs too since 1.6.5
  - `kostra.md` — KOSTRA (municipal reporting, 385 active tables identified by the `kostrahoved` node in `paths`, not by search): `KOK…`/`KOS…` variable IDs instead of `Region`, special region codes (`EAK`, `EAKUO`, `EKG01–17`, `EAFK…`, `EAB`), codelists chosen by *label* because `agg_KOGkommuneregion…` IDs vary per table, all dimensions mandatory, `aggregallowed: false`, estimated/weighted national figures, unrevised figures 15 March → revised 15 June with no `status` flag, KOSTRA groups in Klass 112. Facts verified 2026-09-20. KOSTRA tables and `KOS…` codes churn with reporting requirements, so re-sweep every March/June and expect example URLs here to break more often than elsewhere; never hard-code `agg_KOG…` IDs in examples. 13526 and 12134 are the checker's KOSTRA fixtures
  - `output-formats.md` — `json-stat2`, `csv`, `xlsx`, `html`, `px`, `parquet` and parameters (`UseCodesAndTexts`, `IncludeTitle`, `heading`/`stub` pivoting). Holds the full parquet column contract (`value`/`ContentsCode_{code}` plus the `_symbol` columns that carry `status`), and since 1.6.3 the recommendation to use `xlsx` when data goes into Excel (numeric cells; Excel picks the decimal mark, whatever `lang`). `SKILL.md` only points here
  - `common-tables.md` — well-known table IDs (KPI, befolkning, etc.); the machine-checked table (`| id | title | frekvens | … |`) is parsed by `check_common_tables.py`, so keep the column order. The **Innhold** list at the top names every `##` topic with keywords; add a line there when you add a topic
  - `troubleshooting.md` — common errors and fixes; also the canonical list of SSB's standardtegn (`.`, `..`, `:` plus the pre-2021 symbols) under «NULL-verdier i data» — `json-stat2.md` points here rather than repeating them
  - `mcp-tools.md` — mapping between `pxweb-mcp` MCP tools (`@jarib/pxweb-mcp`) and API endpoints, plus limitations (lossy `search_tables`, no `codelist[Var]` in `fetch_metadata`, no `outputFormatParams`) and the `--url` config caveat. Facts are version-bound — re-verify against the package source when it ships a new major version.
- `CHANGELOG.md` and `DEVLOG.md` — two logs for two readers, both in Norwegian. `CHANGELOG.md` ships in the zip and tells **users** what is different in the answers: a few bullets per version, no sweep counts, no sibling checks. `DEVLOG.md` is the **maintainer's** record and is not shipped: what changed, what was verified live and when, and every sibling-check outcome. It is the old `CHANGELOG.md`, split off on 2026-10-05, when it had grown to nearly twice the size of `SKILL.md`. Every version appears in both. The `CHANGELOG.md` header links to `DEVLOG.md` by full GitHub URL, because a relative link is dead inside the zip.
- `evals/eval-scenarios.md` — maintainer-internal behavioral fixtures: typical user questions with the expected table ID and endpoint sequence. Run via the `skill-creator` skill after larger edits to `SKILL.md` or `references/`. This layer catches *routing* regressions (picking discontinued 03013 instead of 14700); the Python checkers catch *factual* regressions. When an eval fails, run `check_examples.py` first — the table may have changed, not the skill.
- `evals/trigger-eval.json` — trigger fixtures for the frontmatter `description`: 20 queries in skill-creator's `run_eval.py` format (`query`, `should_trigger`, plus `id` and the expected `route`), 10 that should trigger and 10 near-misses that belong to a sibling skill or to none. The behavioral evals hand the agent the skill and the checkers test URLs, so only this layer notices a skill that stops triggering. Unpatched `run_eval.py` undercounts here: it counts calls to its temporary copy, but the installed skill (a symlink to this folder, same description) takes them — detect the installed skill by name instead, and run `claude -p` in a neutral directory, because the model sees its cwd and a path that names the skill biases it. Run it with a `pxweb-mcp` server connected — that is the condition that discriminates, because with MCP tools available a model can go straight to them without loading the skill. A server name without «pxweb» or «ssb» is untested. Results, with model and date, go in `DEVLOG.md` (1.6.4 holds the current baseline).
- `docs/` — user-facing but deliberately **outside the zip**: `brukerveiledning.md` (how to use the skill: prerequisites, the `*.ssb.no` allowlist, example questions, troubleshooting, MCP setup) and `instruks-kort.md` (SKILL.md condensed to one page, to paste into Claude Project instructions, ChatGPT custom instructions or an API system prompt). They are for platforms and readers that never load the zip, and keeping them out also stops a model from loading the condensed copy as if it were the skill. `skillkart-arbeidsflyt.svg` (the Steg 1–6 workflow: endpoints per step, routing to sibling skills, the `/data` response as the only source of numbers) and `skillkart-sjekk-og-pakking.svg` (the check/zip pipeline) are hand-drawn and are the only copy of each drawing: `skillkart.html` wraps them with `<img>` and prose, and `brukerveiledning.md` embeds the workflow SVG so GitHub renders it. Each SVG carries its own `<style>` and an opaque background, since GitHub serves it as an image and no page CSS or web font reaches it — size text for wide fallback fonts like DejaVu Sans. Both name the version they were drawn from; no checker reads `.svg` or `.html`. `llms.txt` is a draft **proposal to SSB** for `data.ssb.no/llms.txt` (llmstxt.org **v2**, English): it links to SSB's own docs, not to this repo's files, so keep it standalone. v2 rules to keep: free-text rules go *before* the first H2 with no heading of their own, every H2 section is a pure `- [name](url): note` list, and links should point to LLM-friendly content (raw GitHub, JSON, `.md` versions where they exist). `check_examples.py` scans `docs/*.md` and `docs/*.txt`, so their example URLs stay live-checked.
- `scripts/`, `.github/` — repo-internal tooling, deliberately excluded from the distribution.

## Editing guidance

- The **Dataintegritet** section at the top of `SKILL.md` outranks everything else in the skill: never state a number not fetched from the API in that conversation, never blend other sources, never interpolate. Don't weaken or relocate it — the rest of the workflow assumes it.
- Preserve the bilingual (Norwegian primary, English secondary) trigger surface in `SKILL.md` frontmatter — removing keywords will cause the skill to stop firing for real user queries.
- The API base URL and endpoint table in `SKILL.md` are the canonical contract; if an endpoint is added/changed upstream, update `SKILL.md` first, then cross-check `references/api-details.md`.
- Examples should use real, currently-published SSB table IDs. `check_examples.py` fails on any table with `discontinued: true`, so replace rather than annotate dead IDs.
- For example URLs/queries, hit the live API and confirm HTTP 200 (or just run `check_examples.py`). Codelist prefixes are easy to forget: `agg_KommFylker` requires `F-` codes, `agg_KommSummer` requires `K-` codes. A 400 response usually means a missing prefix or a missing required variable (`Tid`/`ContentsCode` are never eliminable) — read the `title` field, which is the diagnostic; `detail` is only set for `Too many cells selected`.
- Use `valueCodes` (camelCase) consistently in GET examples — matches the OpenAPI spec and the POST body shape, even though the API is case-insensitive.
- Keep `references/*.md` focused; `SKILL.md` should stay the overview and defer detail to references rather than duplicating it.
- Keep SKILL.md lean: add only what helps many users or tables. One-table quirks and discrepancies SSB already explains in a note go to references, DEVLOG or chat (maintainer, 2026-10-13). But a line that repeats a rule can stay where the agent acts — beside an example or in the step it is about — and a line may only be cut if its content stands elsewhere (maintainer, 2026-10-14, when trimming for 1.6.3).
- Dates in the skill files go on snapshot facts only, written on the fact itself («per 2026-10-24», «0 av 89 (2026-10-11)»): counts, «gjeldende» IDs, observed SSB behaviour — they tell the agent the number may be stale and the API wins. The record of what was verified when belongs in `DEVLOG.md`. Don't add new «Verifisert …:» lead-ins before URL lists; `check_examples.py` checks every example URL, Klass included, on each run. Existing lead-ins mostly also date numbers in the same paragraph, so leave them (maintainer, 2026-10-24).
- `check_examples.py` extracts POST bodies by brace-counting, so a JSON body in the docs must not contain `{` or `}` inside string values, and must not be interrupted by a closing code fence.

### Release checklist (every content change)

1. Bump `metadata.version` in `SKILL.md` frontmatter (semver: PATCH for fact fixes, MINOR for new content). A version that isn't bumped lies about copies being current. `SKILL.md` also states the version in prose ("Denne kopien er v…") — update both.
2. Add a `DEVLOG.md` entry. Existing entries record the verification date and whether the sibling SCB skill was affected; follow that pattern. Then add the user entry in `CHANGELOG.md`, derived from it: what is different in the answers, in a few bullets, with corrections marked **Rettet:**. Same version and date in both files.
3. Rebuild the zip with `scripts/build_zip.sh` — the `zip-sync` CI job fails otherwise.
4. If you added a file to `references/`, update the file tree in `README.md` too (it's hand-maintained; `build_zip.sh` globs `references/*.md` so the file ships either way).
5. If you changed a rule in `SKILL.md`, check whether `docs/instruks-kort.md` still says the same thing — it is a condensed copy and names the version it was condensed from (`docs/brukerveiledning.md` names a version too). If you changed a step, an endpoint or a routing target, redraw `docs/skillkart-arbeidsflyt.svg` as well. Neither is in the zip, so `zip-sync` will not catch them drifting.
6. Update the version column for this skill in the root `README.md` (both the Norwegian and the English table). It is outside the skill folder and outside the zip, so nothing checks it.

**The zip and the README file tree contain user-facing files only**: `SKILL.md`, `README.md`, `CHANGELOG.md`, `references/`, plus `LICENSE` in the zip. Never add `scripts/`, `.github/`, `CLAUDE.md`, `DEVLOG.md` or `evals/` to either; `docs/` is user-facing but stays out of the zip (see Layout).

`LICENSE` (MIT) lives in the **repo root** and covers the whole repo; `build_zip.sh` copies it into the package because MIT requires the notice to travel with every copy, and the zip is the copy that gets handed out. Don't add a per-skill `LICENSE` — edit the root one, and rebuild **all six** zips when it changes (every zip-sync workflow has `LICENSE` in its `paths:` filter). `SKILL.md` frontmatter carries `license: MIT. LICENSE has complete terms` (the optional Agent Skills field — keep it short, it names the file beside `SKILL.md` in the zip); never put licence text in the body, which is loaded on every trigger.

## Related sibling skills

A parallel `scb-pxwebapi-v2` skill exists for Sweden's SCB. The two APIs share the PxWebApi v2 shape — when fixing a bug in one, check whether the other needs the same fix, and record the outcome of that check in `DEVLOG.md` (including "does not apply", with the date). It stays out of `CHANGELOG.md`, which is about this skill's answers.

A third-party `norges-bank-api` skill (github.com/avocodetoast/norges-bank-api-skill, SDMX — not PxWebApi) covers Norges Bank data, and `ssb-histstat` covers digitised historical statistics from before the Statistikkbank era. `SKILL.md` Steg 1 routes such questions there; Steg 5 and Fallgruver require answers to comment only on the fetched SSB numbers — cross-references are routing, **never** data blending from other sources. Keep these references when editing.
