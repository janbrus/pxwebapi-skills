**Addendum 2026-09-09, before 0.11.0 was committed** — ported from the `ssb-pxwebapi-v2` 1.5.0 review of SSB's own user guide, each item re-verified on SSB, SCB and Latvia the same day before being written here:

- **Corrected: expressions and explicit codes can share one `valueCodes`.** "Use one as the sole element" was wrong — `["2015", "top(2)"]` (POST) and `valueCodes[Tid]=2015,top(2)` (GET) return 2015 plus the two newest periods on all three installations. What remains true is that two *function* expressions give the union. `codelists-and-filters.md` and Step 4 reworded
- **Corrected: variable and value codes are not case-sensitive.** `troubleshooting.md` told the reader to compare names "exactly (case-sensitive)"; `tid`, `contentscode`, `personer1` and `TOP(1)` are all accepted on SSB, SCB and Latvia. Codelist IDs *are* case-sensitive (SSB: `agg_kommfylker` → `Non-existent codelist`; not tested at SCB or Latvia)
- **New: curl needs `-g`.** The brackets in `valueCodes[Var]` are curl's own globbing syntax; without `--globoff` the call fails locally with `curl: (3) bad range in URL`, which looks like an API outage. One sentence in Step 4, a section in `troubleshooting.md`, a paragraph in `codelists-and-filters.md`
- **New rows in the comparison table:** code case (insensitive × 3), expression + code mixing (works × 3), `outputFormatParams` with json-stat2 (400 × 3), CSV charset (`iso-8859-1` at SSB and SCB, `utf-8` **with BOM** at Latvia), GET URL over ~2 100 characters (**404**, not 400, × 3), v1 `/navigation` (404 × 3)
- **New in `api-details.md` Output formats:** parameters apply to csv/html/xlsx only; defaults (codes, no title, comma); comma-separated form in one parameter works everywhere and values are case-insensitive; the CSV charset paragraph; all variables in `stub` = long format; `placement` in a POST body
- **New in `troubleshooting.md`:** 404 for over-long URLs and for `/navigation`; 429 — run large queries sequentially; new 503 section
- **Sibling check:** `scb-pxwebapi-v2` gets the same items in Swedish the same day (curl `-g`, mixing, case, csv charset, 404, 503); `ssb-pxwebapi-v2` already has them from its own review, and receives the search-operator correction this skill flagged in 0.11.0 (SSB's `search-syntax.md` said OR; it is AND — `folkemengde region` 17 hits = `AND` 17, `OR` 1 414). `generic-pxweb-v1-skill`: request side does not apply; one row added to its `v1-vs-v2.md`
- **New: a repeated value code returns 500 with an empty body** — not a 400 with a diagnostic. Two identical codes in one variable are enough (`valueCodes[Region]=0301,0301`), in both GET and POST, on all three installations (SSB, SCB `2023,2023`, Latvia `2020M01,2020M01`; verified 2026-09-09). Overlap between an expression and a plain code is fine (`2026,top(1)` answers 200), so only literal duplicates fail — deduplicate selections built programmatically. New 500 section in `troubleshooting.md`, new row in the comparison table
- **Clarified: the URL-length threshold was bisected.** Today's 404 claim was first tested with 450 *repeated* codes, which trigger the 500 above on their own; the limit is now measured with distinct codes at SSB — 400 codes (2 092 characters) answer, 410 (2 142 characters) do not. The conclusion stands; the evidence is now clean
- **Links updated to the repository name `pxwebapi-skills`** (2026-09-09, no version change): the README pointed to `ssb-api-v2-examples` (which redirects) for the SSB sibling; now relative links to both country skills, and the Claude Code install block gets the symlink alternative

- **Third installation: the Official Statistics Portal of Latvia (CSP), `https://api.stat.gov.lv/api/v2`.** Reported by the maintainer, verified end to end: `/config` (API 2.0.0, `maxDataCells` 10 000, 30 calls per 10 s, CC0, `defaultDataFormat: px`), `/tables` (1 504 tables), `/tables/{id}`, metadata, data via GET and POST, `/defaultselection`, `/codelists/{id}` (404 shape), `/savedqueries/{id}` (404 shape — the endpoint exists). New row in the installation table, in the README, and a new **"Verified differences between installations"** table in `references/api-details.md` with fourteen rows — the evidence behind every "varies by installation" in `SKILL.md`. Trigger words `Statistics Latvia`, `stat.gov.lv` added to the description
- **Corrected: json-stat2 is not the default everywhere.** "Both metadata and data are returned as json-stat2 by default" was true of SSB and SCB and false of Latvia, whose `/data` without `outputFormat` returns a PX file as `application/octet-stream` (`CHARSET="ANSI";…`). Step 4 now opens with "always pass `outputFormat=json-stat2` explicitly"; `troubleshooting.md` names the symptom. Same class of error as the v1 skill's 0.12.0 format-default finding
- **Corrected: how `range()`, `top(N,offset)` and `bottom(N,offset)` are written — and a retraction.** The first draft of this release declared `range()` non-existent after every bare GET (`valueCodes[Tid]=range(2024M01,2024M03)`) returned `400 "Illegal selection expression"` on SSB, SCB and Latvia. **That was wrong, and the maintainer disproved it** with a working URL on 2026-09-09: `valueCodes[VareTjenesteGrp]=[range(07.3,07.4.1)]`. The rule, now verified on all three installations in both directions: in a **GET** URL an expression containing a comma must be wrapped in square brackets, because a bare comma is the list separator; single-argument forms work either way; explicit lists take no brackets. In a **POST** body the bare string is right and a bracketed one fails with `Non-existent value`. The draft's own POST test with bare `range()` had in fact returned 200 — the result was misread inside a wall of JSON. What survives from the draft: two function filters in one array give the union, not an interval. `SKILL.md` Step 4, `codelists-and-filters.md` (new GET/POST table), `troubleshooting.md`, the comparison table and `CLAUDE.md` all rewritten; the SCB sibling, which had been "corrected" the same way, is corrected back
- **Corrected: `role.geo` is installation-dependent.** "If `role.geo` is missing, assume the whole country" (Step 3 and `json-stat2.md`) is wrong at SCB, which sets no `role.geo` on any table with a `Region` dimension (TAB638, TAB6471, TAB5444, all `role: {time, metric}`). SSB (`Region`) and Latvia (`AREA`) do set it. Now: look for a geographic variable in `id` first; only when none exists does the data cover the whole area
- **Corrected: weekly period codes.** `codelists-and-filters.md` said `YYYYWNN` / `2024W01`. SSB writes `2026U35`, SCB `2026V30`, Latvia `2026W13` — three letters on three installations, and quarters are `K` in the Nordic pair and `Q` at Latvia. The time-format table is now per installation, with `Other` (Latvia `IRJ010`: `Time01`, not a date) added. A `W` written from habit returns `Non-existent value` at SSB and SCB
- **Corrected: search truncation matches the stemmed index term.** Step 2 said "`population*` matches anything starting with population". It returns **0** hits at Latvia and at SSB's English index; `popul*` returns 203 and 403. Swedish `folkmängd*` is 0 at SCB, `folkmäng*` 117. The engine is Lucene with a language stemmer, so wildcards must be cut before the ending. A leading wildcard returns HTTP 500 at Latvia. New tip in Step 2, new symptom in `troubleshooting.md`
- **Corrected: SCB does send rate-limit headers — and so does Latvia.** `api-details.md` said SCB announces its limit in `/config` and sends "none"; the SSB 1.5.0 changelog says the same. Both statements came from grepping responses for `x-ratelimit`, which is SSB's spelling. SCB and Latvia use `X-Rate-Limit-Limit: 10s`, `X-Rate-Limit-Remaining`, `X-Rate-Limit-Reset` (verified 2026-09-08 on `/config` and `/tables/{id}`; caught by an eval run, not by the probes). The rate-limit table now has both header schemes and the note that the `-Limit` field carries the window, not the count. Step 4's "one or the other" became "SSB headers only, SCB and Latvia both"
- **New: the default search operator is per installation.** `population region` is `population AND region` at SSB (199 hits; OR gives 1 832) and at SCB (207; OR 1 373), but `population OR region` at Latvia (494; AND 125). Added to Step 2 and to the comparison table. The Swedish sibling's `search-syntax.md` claimed OR and was corrected in the same session; the Norwegian sibling's `search-syntax.md` (committed 1.5.0) still says «Standard mellom ord er OR», which the SSB numbers contradict — candidate for 1.5.1

## 0.10.0 — 2026-08-30

Response-side material ported from the v1 skill's research, plus the corrections that probing turned up. All claims verified against SSB and SCB on 2026-08-30.

- **`references/json-stat2.md` rewritten (35 → ~180 lines).** It was a stub — byte-for-byte the same stub as `scb-pxwebapi-v2`'s, only translated — while the skill is meant to be the vendor-neutral home for exactly this material. New or corrected:
  - **Corrected the `extension` bullet.** It listed `/tables` fields (`firstPeriod`, `lastPeriod`, `discontinued`) as dataset `extension`. Replaced with the real two-level structure: dataset level (`px`, `contact`, `noteMandatory`, `discontinued`) and dimension level (`elimination`, `eliminationValueCode`, `codelists`, `show`, `refperiod`, `measuringType`, `priceType`, `adjustment`, `basePeriod`, `alternativeText`, `noteMandatory`, `categoryNoteMandatory`)
  - **New `extension.px` section** — `aggregallowed` (the only place the "can this table be summed at all" answer appears), `decimals`, `heading`/`stub`, `subject-code`
  - **New dimension-`extension` section**, highlighting `basePeriod` and `measuringType`/`priceType`/`adjustment` — these decide how a number may honestly be described, and were not mentioned anywhere before
  - **New trap: eliminability is readable only from the metadata response.** In a *data* response `extension.elimination` describes the extract you received — `true` only when the returned value set still contains the elimination value — not the table's contract. The inverse holds for `eliminationValueCode`: absent from metadata across a 50-table sweep, but emitted in a data response that includes the total. Both PX elimination forms (`ELIMINATION=YES` vs `ELIMINATION("<value>")`) look identical in metadata
  - **New "What json-stat2 cannot express"** — time periodicity (PX's TLIST; v2's only carrier is `timeUnit` on `/tables`, *outside* the document), eliminated dimensions, codelist provenance
  - **Added `note` and `category.note`** with the `noteMandatory` / `categoryNoteMandatory` semantics, `link.describedby`, and the `status` / `DATASYMBOL1`–`6` explanation
  - **New tooling section** — pyjstat, rjstat, `PxWebApiData` (supports **both** API versions since 1.9.0: v2 via the snake_case `api_data()`/`query_url()`/`meta_data()` interface, v1 via `ApiData()`), json-stat Toolkit CLI, the explorer
- **`references/troubleshooting.md`:** the 400 guidance said "check the `detail` field". Verified wrong — `detail` is set only for `Too many cells selected`, and then only as a copy of `title`. Replaced with a `title`-keyed table of the four observed values, plus the positive finding that the payload shape is **identical across installations**, so the bisection procedure the v1 skill needs is unnecessary here. Also noted that the cell limit is a **400** in v2, not v1's 403
- **`references/api-details.md`:** replaced the 6-field `/config` example with the verified 12-field response. Three points called out — `sourceReferences` gives the agency's own citation string per language, `maxDataCells` spans 5× between the two known installations, and `dataFormats` is per installation (SSB serves `parquet`, SCB does not)
- **`SKILL.md`:**
  - Installation table now lists the five agencies **verified still v1-only** (Finland, Iceland, Faroe Islands, Greenland, Estonia) and routes them to `generic-pxweb-v1-skill`, plus a "which version is this?" recipe. **Check that the body parses as JSON, not the status code** — Statistics Greenland answers `GET /api/v2/config` with HTTP 200, `text/html`, and `CONFIG404;…File not found` in the body

## 0.9.0 — 2026-08-30

Versioning introduced, plus the rules that `ssb-pxwebapi-v2` had and this skill was missing.

- **Versioning introduced** (`metadata.version` in `SKILL.md` frontmatter + this log). A user holding an old copy previously had no way to tell
- **New top section "Data integrity — the base rule"**, placed after the intro and before the installation list: **never state a number you have not fetched from the API in this conversation.** Seven bullets — no numbers from memory, no other sources in the same answer, say so when the API fails, no interpolation, mark your own calculations and keep the API's decimals, show `status` values as they are, check `discontinued`/`lastPeriod`. The rule previously existed only in `ssb-pxwebapi-v2`; the argument is *stronger* here, since this skill can point at any statistical agency. `CLAUDE.md` records that the section outranks the rest, so it does not get relocated or watered down in a later edit
- **Rate limiting: check both `/config` and the response headers.** The two known installations behave in opposite ways — SSB reports `maxCallsPerTimeWindow: 0` in `/config` but sends `x-ratelimit-*` headers (40 per 60 s); SCB reports `30`/`10` in `/config` and sends no headers. The old text said only "check `/config`", which against SSB reads as "no limit". **`0` means "not in use", not "unlimited"**
- **Defaultselection behaviour documented.** A `GET /data` with no selection parameters is not an error and does not return the whole table — it silently returns the default selection (SSB 07459 → `size [360, 1, 1]`, 360 cells, 200; SCB TAB638 → `size [290, 1, 1, 2]`, 580 cells, 200). The dangerous part: 07459 has **five** dimensions and the default selection returns **three** — sex and age were summed away unannounced
- **New rule for the time dimension:** prefer `top(N)`/`from(value)` over `range(from,to)` and explicit periods — relative filters capture new periods automatically, so shareable URLs and saved queries stay current. Matters most for `/savedqueries`
- **Cross-reference to `ssb-chart-skill`** in Step 5, for visualizing SSB data (with the usual "if available in the environment" caveat)
